# 第 4 期｜单评审与四角色正式推理

[主入口与评审设置](./experimental_setting.md) · 使用[第 3 期核验的 8B 硬件配置](./phase3_pilot_budget.md)及固定 C/T 名单，向[第 5 期](./phase5_trust_and_ranking.md)交付原版 8B 缓存。本期占用单卡。

## 1. 实验目标

让 B1 和 B4 在相同候选名单上形成可审计的排名。四角色只运行一次，后续可靠度估计、聚合器对照、角色移除和双边重排共用这些意见。

## 2. 实验内容

| 推理块 | 窗口数 | 输出 |
|---|---:|---|
| C 四角色 | 4,096 窗 | 逐角色选票和逐岗预测，供校准 |
| T 四角色 | 8,192 窗 | B4、T0、T1、W1、F 和角色移除共享的评审 |
| T 综合单评审 | 2,048 窗 | B1 完整选票 |

1. Skill、Trajectory、Preference、Employer 分别核对技能、经历跨度、显式意向和岗位门槛，均预测 `J`。Preference 另外输出 `pC`，Employer 另外输出假设已投递时的 `pE`。各角色独立从同一 BM25 初始榜开始，以自己的上一个窗口写回结果推进。
2. 保存原始窗口编号与岗位映射、输入/输出顺序、概率、token、耗时和重试记录。逐岗概率按主入口 §3.1 截断，在同角色、同人、同岗、同预测头内先平均 logit 再还原。一个有效角色最终只交一张 10 岗选票。
3. 按运行 ID、模型版本、区块、用户、角色、遍数、窗口起点和实际输入顺序识别缓存。恢复前核对前一窗口写回后的顺序。持久失败的角色标记缺失，登记该角色尚未执行的窗口。首轮请求、重试和已完成逻辑窗口分别计数。

**交接产物**为 `base/windows.jsonl`、`base/reviews.jsonl`、失败与缺失明细，以及本期 GPU 账本。选票表至少包含区块、用户、角色、十岗顺序、岗位级预测和状态。

## 3. 验收且可推进标准

- [ ] C、T 用户均能按名单哈希定位。每个计划角色都有“完整选票”或“已记录的失败”这一终态。
- [ ] 每张有效选票都是原十岗的排列。每个有效窗口四个编号无重无漏，所需概率在 `[0,1]`，任取一张有效选票可从 8 个窗口顺序重建。
- [ ] 逻辑工作量能与 14,336 的计划值对账，提前终止、重试和恢复逐项解释。核对缓存哈希并封存后，进入 CPU 上的第 5 期。
